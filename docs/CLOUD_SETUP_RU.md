# Настройка облака ATLAS

Подготовлено 14.10.2026. Ничего не зарегистрировано и не опубликовано. Можно пока продолжать пользоваться SQLite без аккаунта.

1. Создайте проект Supabase в выбранном регионе. Выполните **supabase/migrations/202610140001_atlas_sync.sql** в SQL Editor один раз. Появятся `atlas_snapshots`, `atlas_snapshot_versions` и `save_atlas_snapshot`. У клиентов только SELECT своей строки; INSERT/UPDATE разрешены только внутри RPC с проверкой revision и `auth.uid()`.
2. Скопируйте `.env.example` в `.env`. Укажите `EXPO_PUBLIC_SUPABASE_URL` и **публичный publishable/anon key** в `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Никогда не вставляйте `service_role`, secret key, Google client secret или SMTP пароль в Expo, расширение или публичные файлы. `.env` исключён из Git.
3. Auth → URL Configuration: Site URL = адрес будущего сайта; для локальной проверки допустим `http://127.0.0.1:8085`. Добавьте точные redirect URL: `http://127.0.0.1:8085/auth/callback`, `https://ВАШ-ДОМЕН/auth/callback`, `atlas://auth/callback`. Локальный адрес и `localhost` — разные origin и разные базы браузера.
4. Email provider: включите email login. В шаблоне **Magic Link** используйте код `{{ .Token }}`; приложение вызывает `signInWithOtp` и `verifyOtp(type: email)`. Регистрация включена для нового адреса. Настройте ограничения отправки, срок кода и защиту от массовых регистраций перед открытой бетой.
5. Для реальных адресов настройте свой SMTP. Рекомендован Resend после подтверждения собственного домена и DNS. Встроенный SMTP Supabase ограничен командными адресами/тестированием. SMTP ключ храните только в Supabase. Проверьте доставку, папку спам, повторную отправку, неверный/истёкший код.
6. Google Cloud: создайте OAuth Web Client, настройте consent screen и тестовых пользователей. Redirect URI Google = адрес callback из настройки Supabase Google provider (`https://PROJECT.supabase.co/auth/v1/callback`), а не `atlas://...`. Client ID/secret вводятся в Supabase. Приложение использует PKCE; web переходит полной страницей, native открывает браузерную auth session и получает deep link. Нужна собственная native сборка для точной схемы.
7. Пересоберите приложение после переменных: `npm run build:web`. Разместите `dist` с `_headers`; для Workers предусмотрен `wrangler.jsonc`. COOP `same-origin` и COEP `require-corp` обязательны для текущего SQLite Web. Не добавляйте service worker с кешированием auth callback без отдельной проверки.
8. Профиль → Аккаунт и облако. После входа проверьте адрес пользователя и количества записей. Нажмите **Проверить облачную копию**, выберите направление и подтвердите. Пока нет автоматического фонового обмена или merge. Данные устройства остаются после выхода; для общего компьютера нужна отдельная область хранения в следующем этапе. Никогда не подтверждайте отправку истории другого человека в новый аккаунт.

## Проверка перед включением для пользователей

- Первый вход, отмена Google, неверный email-код, просроченная сессия, перезапуск браузера/телефона.
- Два устройства читают v1: первое записывает v2; второе получает конфликт, его локальная копия сохраняется. Повторно проверить копии и явно выбрать направление.
- Разрыв сети после серверной записи: повторный запрос со старой revision даёт конфликт; не повторять вслепую.
- Аккаунт B не видит A; прямой UPDATE таблицы запрещён. Смена аккаунта во время проверки копий отменяет операцию, RPC также сравнивает ожидаемый user ID.
- Загрузка облака не разрешена при активной тренировке. Перед восстановлением схема backup проверяется, SQLite выполняет транзакцию и сохраняет recovery copy.
- Облачный payload ограничен 500 KB на клиенте / 600 KB для JSONB-текста на сервере. Это ограничение беты связано с текущим синхронным SQLite web bridge; большие истории пока экспортировать локально и исследовать отдельно.
- Последние 20 облачных ревизий доступны владельцу для чтения; экран выбора старой ревизии пока не сделан. Для восстановления выбранной версии извлеките `payload` из собственной строки `atlas_snapshot_versions` и импортируйте JSON через штатный экран.
- Перед публикацией добавить self-service удаление аккаунта/данных, политику конфиденциальности, восстановление/поддержку, мониторинг и проверить все зависимости. Не включать платный тариф до подтверждённого retention.

## Что проверено локально

SQL применяется в настоящем PostgreSQL WASM (PGlite) с тестовыми ролями `anon`/`authenticated` и имитацией `auth.uid()`. Тестируются RLS, grants, запрет прямой записи, CAS, сохранение ревизий, лимит payload. Это не проверка инфраструктуры Supabase, JWT, SMTP, Google или реального сетевого обмена двух устройств.

Официальные справочники: [Email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [Google](https://supabase.com/docs/guides/auth/social-login/auth-google), [Native deep links](https://supabase.com/docs/guides/auth/native-mobile-deep-linking), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp).
