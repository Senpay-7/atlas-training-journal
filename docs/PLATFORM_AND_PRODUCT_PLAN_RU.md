# ATLAS: аккаунты, платформы и план развития

Проверено по официальной документации **14 октября 2026 года**. Это проектное решение и план выпуска; наличие этого файла не означает, что облачный проект зарегистрирован, письма отправляются или приложение опубликовано. Пользователь выбрал подготовку локально, пока без домена и хостинга.

## Рекомендация

Оставить общую кодовую базу Expo для Android, iOS и веба. Сохранить SQLite для работы без сети. Для аккаунтов и общей копии данных выбрать **Supabase Auth + Postgres**, для сайта — **Cloudflare Workers Static Assets**, для писем с кодом — **Resend SMTP** после подключения домена. Это рекомендация для текущей архитектуры ATLAS: SQL, проверяемые транзакции и правила доступа подходят существующей модели программ, тренировок и подходов.

Cloudflare Pages тоже позволяет разместить готовый `dist`, но сама Cloudflare теперь рекомендует новые проекты начинать на Workers. Переписывать React Native Web в отдельную вручную поддерживаемую HTML-версию не требуется: web export уже является HTML, JavaScript, стилями и ресурсами сайта. [Cloudflare Pages](https://developers.cloudflare.com/pages/), [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/).

Расширение на первом этапе разумно выпускать как небольшой помощник, открывающий ATLAS в отдельной вкладке. Вход и данные тогда принадлежат обычному сайту. Полноценное независимое приложение внутри расширения — отдельный этап с собственной упаковкой и тестами; такой помощник нельзя называть автономной офлайн-версией расширения.

## Что можно подготовить без облачного аккаунта

- Интерфейс входа, состояния отсутствующей конфигурации, ошибки, выход из аккаунта и договорённость о синхронизации.
- SQL-миграции, правила доступа, адаптер синхронизации и тесты конфликтов на локальных данных.
- Web export, примеры конфигурации хостинга и локальный пакет расширения для проверки через режим разработчика.
- Android/iOS исходники и настройки сборки. Экспорт JavaScript/Hermes не равен подписанному APK, AAB или IPA.

Настоящие Google OAuth, отправка email и обмен между устройствами потребуют созданных проектов, ключей и проверки на двух реальных клиентах. Локальный Supabase можно поднять через CLI и совместимую с Docker среду; это отдельная инфраструктура, а не часть уже имеющейся SQLite. Нельзя показывать успешную облачную синхронизацию при отсутствии соединения с сервером. [Локальная среда Supabase](https://supabase.com/docs/guides/local-development/cli/getting-started).

## Вход и разделение аккаунтов

**Email-код.** Использовать `signInWithOtp`, затем `verifyOtp` с `type: 'email'`. В шаблоне письма Supabase должен присутствовать `{{ .Token }}`, иначе стандартный сценарий может отправлять ссылку. Регистрация нового адреса включена в этом методе по умолчанию; интерфейс должен ясно объяснять, что одно действие выполняет вход или создание аккаунта. Учитывать серверные ограничения повторной отправки и срок действия кода, а не обещать свои значения без настройки сервера. [Email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless).

**Письма.** Встроенный SMTP Supabase предназначен для разработки: сейчас он отправляет только адресам участников команды проекта и ограничен двумя письмами в час. Для пользователей нужен собственный SMTP. Resend требует подтверждённый домен; его ключ задаётся в серверных настройках Supabase, не в приложении и не в расширении. [Ограничения SMTP Supabase](https://supabase.com/docs/guides/auth/auth-smtp), [Resend + Supabase](https://resend.com/docs/send-with-supabase-smtp).

**Google.** Создать Google Cloud OAuth client, включить провайдер в Supabase, указать callback Supabase в Google и точные разрешённые адреса возврата в Supabase. Секрет Google хранить у провайдера. В клиенте использовать PKCE, хранить verifier до завершения операции и обменивать полученный `code` через `exchangeCodeForSession`. Удалять код из адресной строки после успешного обмена; не писать коды или токены в журналы. [Google provider](https://supabase.com/docs/guides/auth/social-login/auth-google), [PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

Для веба предпочтителен переход в той же вкладке: нужный SQLite заголовок COOP может нарушать связь OAuth popup с открывшей страницей. Для native нужны обработчик deep link и собственная development/production сборка; имеющаяся схема `atlas` позволяет подготовить адрес вроде `atlas://auth/callback`, но адрес должен совпадать с реально реализованным маршрутом. На выпуске предпочтительны проверенные universal/app links. [COOP и popup](https://web.dev/articles/cross-origin-isolation-guide), [Native deep linking](https://supabase.com/docs/guides/auth/native-mobile-deep-linking).

Предлагаемое правило данных: гостевой профиль и каждый `user.id` имеют отдельную область хранения. Первый вход предлагает перенести гостевую историю или использовать облачную; смена аккаунта не загружает автоматически историю предыдущего человека. Токены не входят в JSON-экспорт тренировок. Для native нужен защищённый адаптер хранения сессии; веб требует защиты от XSS и точных разрешённых URL. Выход завершает сессию и очищает её секреты, но удаление сохранённых тренировок должно быть отдельным явным действием.

## Синхронизация: первый надёжный объём

**Фактическая реализация 0.2:** подготовлены email/Google PKCE, ручная передача копий, backup v3 (импорт 1/2/3), SQL/RLS/CAS и 20 сохранённых облачных ревизий. Лимит клиента 500 KB. Автообмен и отдельные локальные базы каждого аккаунта пока не включены; интерфейс предупреждает, что данные остаются на устройстве после выхода и требует явного направления и подтверждения. Подробности: CLOUD_SETUP_RU.md. Раздел ниже описывает архитектуру дальнейшего развития; исходное предложение v2 обновлено до v3.

Существующий `src/services/backup.ts` проверяет формат backup 1/2, ссылки между сущностями, уникальность, завершение подходов и XP; текущий экспорт — версия 2. Для первого облачного этапа можно использовать **проверенный снимок backup v2**, не синхронизируя установленный каталог и картинки. Это архитектурное предложение, а не готовый распределённый merge.

Облачная запись: `user_id`, `revision`, `payload`, `updated_at`. Сервер определяет владельца через `auth.uid()` из проверенной сессии. RLS разрешает читать только собственную строку. Публичный ключ проекта допустим в клиенте при правильно настроенных RLS и правах; `service_role`/secret key в приложение не включать. Запись выполнять через ограниченный RPC, чтобы клиент не мог обойти проверку версии прямым `UPDATE`. Для функции с повышенными правами нужны фиксированный `search_path`, проверка пользователя и минимальные grants. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Алгоритм, который следует реализовать и проверить:

1. Сохранить тренировку в SQLite. Сеть не должна блокировать этот шаг.
2. Зафиксировать снимок и его локальную версию; отправить его с последней известной серверной `revision`.
3. В одной серверной транзакции сравнить ожидаемую версию и записать следующую. Две конкурентные загрузки одной версии не могут обе пройти. Конфликт возвращать как отдельный результат, например HTTP `409` при наличии HTTP-обёртки.
4. При конфликте оставить обе копии доступными. Предложить загрузить облачную или явно заменить её локальной, предварительно сохранив восстановимую копию. Повторная попытка использует свежую revision; не делать автоматический «последний запрос победил».
5. Проверять скачанный снимок через ту же схему перед транзакционным восстановлением. Не заменять незавершённую тренировку неожиданно.
6. Помечать локальное состояние синхронизированным только если оно не изменилось во время запроса. Повторный сетевой запрос должен быть идемпотентным либо распознавать уже загруженный снимок.

Ограничения этапа: снимок целиком становится дорогим при большой истории; параллельное редактирование двух устройств требует выбора копии. В установленном `expo-sqlite/web/WorkerChannel.ts` синхронный ответ ограничен буфером 1 MiB: разрешённый парсером JSON-экспорт до 20 MB не означает, что web уже обработает такой объём. Нужны нагрузочная проверка и переход на асинхронное постраничное чтение до масштабирования. При росте перейти на таблицы и очередь изменений по сущностям с устойчивыми ID, версиями и отметками удаления. Не называть один последний снимок полноценной историей резервных копий. Тесты: два устройства, две вкладки, обрыв сети после серверной записи, смена аккаунта, отменённый вход, недоступный проект, старый backup и неизвестная будущая версия.

## Сайт: конфигурация для будущего размещения

SQLite для веба требует WebAssembly и cross-origin isolation; официальная документация Expo всё ещё обозначает эту поддержку как alpha. Открытие `index.html` через `file://` не заменяет запуск через HTTP(S). Проверять OPFS, перезагрузку, квоты и поддержку браузера отдельно. [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/).

Пример будущего `wrangler.jsonc` для статического SPA; здесь приведён только пример, деплой не выполнен:

```json
{
  "name": "atlas-training",
  "compatibility_date": "2026-10-14",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application"
  }
}
```

Пример `dist/_headers` (обычно исходник хранится в `public/_headers`, чтобы переживать пересборку):

```text
/*
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
```

Такой строгий COEP подходит локально упакованным изображениям и WASM; будущие внешние ресурсы должны отдавать совместимые CORS/CORP-заголовки. Проверить `crossOriginIsolated`, загрузку worker/WASM и возврат OAuth в production. Правила `_headers` относятся к статическим ответам; при добавлении функций их ответы получают заголовки в коде. Для Pages также нужна SPA-навигация на вложенные пути и callback после обновления страницы. [Workers headers](https://developers.cloudflare.com/workers/static-assets/headers/), [Pages headers](https://developers.cloudflare.com/pages/configuration/headers/).

Пример публичной конфигурации клиента, без настоящих ключей:

```dotenv
EXPO_PUBLIC_SUPABASE_URL=https://PROJECT_REF.supabase.co
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_REPLACE_ME
EXPO_PUBLIC_WEB_URL=https://YOUR_DOMAIN
```

Названия переменных должны совпасть с реализованным адаптером. `EXPO_PUBLIC_*` встраиваются в клиент, поэтому SMTP-ключ, Google client secret и серверные ключи здесь недопустимы. До регистрации сервисов значения оставляются пустыми/отсутствующими, а приложение продолжает работать локально.

## Chrome и Edge

Для полного packaged MV3 все выполняемые JS/WASM должны входить в пакет. Удалённые JSON-данные допустимы как данные; загрузка кода приложения с CDN не подходит. CSP не разрешает обычный `unsafe-eval`; WebAssembly требует `wasm-unsafe-eval`. Имеющийся Expo export нужно отдельно проверить на inline-скрипты, абсолютные пути ресурсов и маршрутизацию в `chrome-extension://`. [Remote hosted code](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code), [Extension CSP](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy).

Часть manifest для будущей полноценной версии с SQLite, **не готовый manifest расширения**:

```json
{
  "manifest_version": 3,
  "content_security_policy": {
    "extension_pages": "script-src 'self' 'wasm-unsafe-eval'; object-src 'self'"
  },
  "cross_origin_opener_policy": { "value": "same-origin" },
  "cross_origin_embedder_policy": { "value": "require-corp" }
}
```

Isolation может задаваться ключами manifest. OAuth полноценного расширения использует поддерживаемый Identity flow и согласованный redirect, а не обмен токенами через произвольную страницу или query string. Для стартового расширения, которое только открывает сайт, отдельный OAuth и доступ к истории браузера не нужны. [Extension COEP](https://developer.chrome.com/docs/extensions/reference/manifest/cross-origin-embedder-policy), [Identity API](https://developer.chrome.com/docs/extensions/reference/api/identity).

Edge совместим со многими Chromium API, но требует собственной проверки пакета и ограничений. Обещание «любой браузер» преждевременно: Firefox и Safari потребуют отдельных проверок и, возможно, вариантов сборки. Публикация в магазинах также требует отдельной карточки, описания данных и проверки. [Перенос в Edge](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/port-chrome-extension).

## Продуктовый взгляд и расширение

Это рабочие гипотезы по продукту, без проведённых интервью и доказанной готовности платить.

**Сильная основа:** быстрый запуск тренировки, своё расписание, сохранение без сети, три языка, доступный экспорт и общая логика на платформах. Визуальная демонстрация упражнения полезнее декоративной анимации, если помогает человеку понять исходное положение и движение.

**Главный риск интерфейса:** превращение тренировки в длинную форму. Основной экран должен показывать назначение «3 × 10» и одно действие отметки; изменение программы доступно через меню, а фактические результаты отделены от назначения. Новые анимации не должны задерживать отметку подхода. Для демонстраций нужны старт/пауза, ручное повторение и понятное состояние при уменьшенном движении. Сгенерированный материал до проверки человеком помечать как демонстрационный; красивое изображение само по себе не подтверждает правильную технику.

| Приоритет | Следующий результат | Что измерить |
|---|---|---|
| P0 | Компактный трекер, редактирование через меню, качественные проверенные демонстрации | Время до первого подхода; завершение первой тренировки; ошибки изменения плана |
| P0 | Реальный вход и безопасное восстановление между двумя устройствами | Успех получения/ввода кода; успешная синхронизация; конфликты без потери данных |
| P1 | Небольшой курируемый каталог сплитов с источниками, версией и оборудованием | Выбор → запуск → повторное использование через неделю |
| P1 | Установки web/native и Chrome/Edge helper | Доля пользователей, которым действительно нужна каждая платформа |
| P2 | Аналитика прогресса, периодизация, совместная работа с тренером | Удержание 4 недели; использование функции; готовность платить |

Не импортировать платные авторские программы целиком без прав. Указывать источник, что является оригиналом, адаптацией или собственной программой ATLAS. Публичная доступность текста/видео не означает разрешение на перепубликацию. Расширение каталога следует делать через декларативные пакеты, сохраняя источники и проверку данных; подробный реестр уже ведётся в `SOURCE_AUDIT_RU.md` и `MEDIA_LICENSING.md`.

**Монетизация для проверки:** бесплатный журнал, базовые программы, локальное хранение и экспорт; подписка за расширенную аналитику, историю облачных версий, большие медиа-пакеты и дополнительные инструменты планирования. Позже — лицензированные авторские пакеты с разделением выручки и кабинет тренера. Уже созданная история и возможность её выгрузить остаются доступны после отмены подписки. Рекламу в процессе тренировки и продажу тренировочных данных в первую модель не включать. Цену определять после интервью и теста предложения, а не считать желаемую подписку подтверждённым спросом.

Для проверки экономики считать: активные пользователи → доля платящих → поступления минус комиссии, сервисы, доставка медиа, поддержка и лицензии. Пока эти значения не измерены, прогноз прибыли не делать.

## Условия первого публичного выпуска

1. Владелец создаёт выбранные сервисы и домен; применяются миграции/RLS и точные redirect URL, подключается SMTP. Секреты остаются в серверных настройках.
2. Проверяются реальные входы, выход, удаление аккаунта/облачных данных, восстановление, конфликт двух устройств и перенос гостевой истории. Подготовлены понятные правила конфиденциальности и контакты поддержки.
3. Web проверяется на HTTPS, прямых ссылках, обновлении страницы, OPFS и OAuth; native — на физических Android/iOS, включая фон, таймер и deep links. Расширение — отдельно в Chrome и Edge.
4. Проверяются лицензии каждого материала, три локализации, reduced motion, читаемость и работа без сети. Упражнения и демонстрации проходят содержательную проверку.
5. Выпуск начинается с ограниченной беты и возможности отката; затем магазины и платные функции. До этого интерфейс и отчёт явно отличают локально подготовленные возможности от подключённых и проверенных в облаке.
